Section 1

Overall shape: one aggregate, forward-only edges

Everything hangs off a single aggregate root. A Campaign (types/Campaign.ts) owns ten required entity arrays — articles, adventures, npcs, locations, factions, items, sessionLogs, playerCharacters, plots, notes — one optional array (secrets?, the only entity array an older save may legitimately lack), and non-array live state: activeEncounter?, activeSceneId?, activeSessionId?, pinnedEntities?, dmStyle?, featureOverrides?, wizardDismissed?, styleProfile?, gcpApiKey?. Scenes are the one nested entity kind: they live only inside Adventure.scenes, yet are id-addressable everywhere (pins, mentions, the graph view, session planning).

Three properties define how the model behaves as a graph:

  • Edges are stored forward-only. Every reference is an id (or id array) on the source entity. "Backlinks" are never stored — they are derived by scanning the campaign (utils/backlinkUtils.ts), which at localStorage scale (hundreds of entities) is a sub-millisecond full sweep.
  • Three edge pairs are bidirectionally maintained by the store itself (NPC↔Faction membership and the Location and Article hierarchies); everything else is a one-way pointer whose integrity is preserved by cascade deletion rather than reciprocal writes.
  • Untyped id-sets form a second overlay graph. mentionedEntityIds, relatedEntityIds, linkedEntityIds, taggedEntityIds, and pinnedEntities can point at (nearly) any entity kind; they power backlinks, AI context, and navigation, and are resolved by scan against every collection.

Each card lists the entity's key field, its file, and its outbound edges. Section 7

Integrity machinery

Integrity is enforced in services/campaignService.ts (all writes flow through it via Immer) plus the two ingestion paths. The contract, path by path:

  • Bidirectional sync — _synchronizeNpcFactionLink, _synchronizeLocationHierarchy, _synchronizeArticleHierarchy run inside the normal updaters (updateNpc({factionId}), updateLocation({parentLocationId}), …). There are no dedicated "link" methods; the relationship field is the API.
  • Cycle guards — _isLocationParentingAllowed / _isArticleParentingAllowed reject any re-parenting that would close a loop, and their ancestor walks carry visited-sets so a pre-existing cycle in imported data cannot hang them. AI batch-add runs the same guard on name-resolved parents. Editors' possibleParents walks are guarded identically.
  • Cascade deletion — every one of the 12 delete methods calls the central sweep _purgeEntityReferences(campaign, id), which clears the deleted id from: NPC relationships + mentionedEntityIds + history[].referenceId; Location mentionedEntityIds + connections + history[].referenceId; Faction leaderId/headquartersLocationId/memberIds; Scene locationId/npcIds/mentionedEntityIds; Article/Plot relatedEntityIds + mentionedEntityIds; SessionLog planning ids, relatedPlotIds, plotProgressions keys, structuredNotes[].taggedEntityIds; Secret linkedEntityIds/revealedInSessionId; pinnedEntities. deleteAdventure additionally runs the sweep for every contained scene id.
  • Duplicate / template import — duplicateCampaign and importTemplateData do a two-pass id remap: pass one mints new ids for every entity and nested sub-object (scenes, PoIs, loot, history entries), pass two rewrites every edge through the map — idMap.get(id) ?? id on duplicate (preserve external refs) vs. remap-or-drop on template import (no dangling refs from partial payloads).
  • JSON import — validateImportedCampaign (services/importExportService.ts) structurally validates, backfills required arrays (normaliseRequiredArrays), dedupes ids campaign-wide including nested collections, and rejects files whose envelope version exceeds CURRENT_CAMPAIGN_VERSION before any mutation.
  • Versioning — the Campaign interface itself is unversioned; version exists only on the exported JSON envelope. In-memory/localStorage payloads are upgraded structurally by migrateCampaignsData (shape-sniffing, e.g. legacy plots[].name → title), which backfills every required array and is kept in lockstep with normaliseRequiredArrays.

The standing risk this design carries: integrity is a hand-maintained N-place contract. A new edge type must be registered in the purge sweep, both remap passes, the backlink scanner, the continuity checker, the graph view, and (if AI-visible) the context builder. The highest-leverage future refactor is a single forEachReference(campaign, visitor) edge registry that those six consumers share — turning "add an edge" into a one-place change.

Section 10

AI wire shapes — what generation is allowed to say

AI output never carries store-owned fields. types/Evocation.ts encodes the omission contract:

  • AdventureForBatchAdd = Adventure minus id/scenes, with scenes minus id and with status/npcIds optional — the real provider's scene schema never returns them, so consumers of the raw shape get a compile error instead of a false promise. Normalization to full Scenes (defaulting status: 'planned', npcIds: [], skillChecks: []) happens in exactly two places, both in campaignService.ts: createFullAdventure and batchAddToCampaign, each building from createDefaultScene() and spreading AI data over it.
  • BatchAddData applies the same rule per kind: NPCs omit id + knowsPlayerHistory; locations omit id + subLocationIds; factions omit id + leaderId + memberIds; items omit id. batchAddToCampaign resolves AI-returned faction/location names or ids to real ids and establishes the bidirectional links (membership, hierarchy — cycle-guarded) itself.
  • The world simulation goes further: WORLD_SIM_WRITABLE_FIELDS allowlists prose fields only — the simulation can narrate change but can never rewire ids, arrays, or edges.
